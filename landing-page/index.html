Browser automation

TurboSheet is a high-performance browser automation framework for Node.js, built in Rust via napi-rs. Native test runner, component testing, trace viewer, visual regression, and network interception — all running directly against the browser protocol with zero JSON serialization overhead.

Features

Everything you need
for browser automation.

⚡

Rust-Powered Core

Every browser interaction runs through Rust via napi-rs. Zero-GC overhead, direct CDP protocol access via chromiumoxide, and native thread-level parallelism out of the box.

▷

Built-in Test Runner

Describe, test, and expect — all native Rust functions. Multi-reporter output (dot, list, html, json, junit, github), sharding, retries, timeouts, and parallel workers.

◎

Component Testing

Mount React, Vue, or Svelte components directly with mount(). Interact via locator API, get props and state, wait for conditions — all without a separate test framework.

◉

Locator API

Role, text, label, placeholder, alt text, title, and test ID selectors. Chainable filter, first, last, nth. Actions: click, fill, hover, focus, check, select, double-click — matching Playwright's ergonomics.

⊞

Trace Viewer

Record all interactions during test execution. Serialize and deserialize traces, generate an interactive HTML viewer, and export events as JSON for custom analysis.

⊕

Visual Regression

Pixel-level screenshot comparison with configurable thresholds. Generate diff images, save snapshots, and integrate with the test runner for automatic pass/fail判定.

◈

Video Recording

Record browser sessions with configurable FPS, quality, codec (VP8, VP9, H264, H265), and retention policy (always, on-failure, never). Per-page or per-context.

↗

Network Interception

Route, modify, and mock network requests with page.route(). Inspect request/response headers, bodies, and status codes — ideal for testing edge cases and offline scenarios.

⎇

Swarm & CLI

Redis-backed parallel execution across machines with --swarm. CLI includes test runner, codegen, debug mode, migration from Playwright/Cypress, and CI initialization.

Architecture

Built for performance,
not hype.

// napi-rs

Zero-Copy FFI

No JSON-RPC bridge between Node.js and the browser driver. Rust communicates directly via napi-rs buffers and function calls — eliminating serialization overhead entirely.

// chromiumoxide

Direct CDP Protocol

Uses the chromiumoxide Rust library for native Chrome DevTools Protocol handling. No subprocess orchestration, no HTTP translation layer — just direct WebSocket commands.

// engines

Feature-Flagged Engines

Chromium is the default and most mature engine. Firefox (WebDriver BiDi) is configurable via the bidi feature flag. WebKit support is under active development behind the webkit feature flag.

// wasm

Edge & WASM Targets

Experimental compilation target for wasm32-wasi via the edge feature, enabling browser automation from serverless, edge runtime, and lightweight container environments.

Simple API

Write less. Automate more.

example.mjs 
// Page automation with locator API
import { launch, test, expect, mount } from 'turbosheet';

const browser = await launch({ headless: true });
const ctx     = await browser.newContext();
const page    = await ctx.newPage();
await page.goto('https://example.com');

const button = page.locator('button#submit');
await button.click();

// Component testing
const component = await mount('<Counter />', { framework: 'react' });
await component.locator('button').click();
const html = await component.content();

// Built-in test runner
test('homepage loads', async () => {
  await page.goto('https://example.com');
  expect(await page.title()).toBe('Example Domain');
});

Implementation Roadmap

Phase 0 · Quick Wins NOW 1-2 wks
Wire existing but unwired subsystems end-to-end.
Wire reporters to executor, CDP screencast → video recording, trace per test, implement Keyboard.press(), enable assertion engine tests
Phase 1 · Test Runner Core 3-4 wks
Users can define and run tests end-to-end with reporting.
Implement test()/describe()/hooks, wire all 7 reporters to executor, add skip/only modifiers, sharding, config file parser
Phase 2 · Auto-Waiting & Actionability 3-4 wks
Reliable interactions without explicit waits.
Visibility/enabled/stability checks before actions, stale element retry, configurable action timeout, force option, proper Locator struct
Phase 3 · Locator Engine Completion 2-3 wks
Parity with Playwright locator API for all query patterns.
XPath/text= selectors, .and()/.or() combinators, locator.all(), strict mode, soft assertions, expect.poll()/toPass()
Phase 4 · Error Hierarchy & Events 1-2 wks
Production-quality error types and complete event system.
Typed errors (TimeoutError, LocatorError etc.), wire missing events (requestfailed, download, frame), removeListener(), waitForEvent()
Phase 5 · Firefox & WebKit Completeness 4-6 wks
All 3 engines have comparable feature sets.
Implement ~75 Firefox stubs and ~80 WebKit stubs, shared WebDriver utility layer, evaluate BiDi support
Phase 6 · CLI, CI/CD & Configuration 2-3 wks
Production CI/CD integration.
CLI binary with all flags, config file (tsheet.config.ts/json), Docker image, CI-specific optimizations
Phase 7 · Advanced Features 6-8 wks
Parity on advanced use cases.
Frame/worker support, WebSocket interception, accessibility snapshots, device profiles, HAR import/export, raw CDPSession
Phase 8 · Enterprise Readiness 4-6 wks
Production-scale testing infrastructure.
Watch mode, UI mode / time-travel debugger, codegen, flaky detection, plugin auto-discovery, cloud dashboard
