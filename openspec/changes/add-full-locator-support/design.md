## Context

The codebase has two parallel locator systems:

1. **Rust `JsLocator`** (`src/locator.rs`, ~740 lines) — Full Playwright-compatible locator with actionability checks, get-by methods, filtering, chaining, frame scoping. Already exposed via `napi` on `JsPage` (`page.locator()`, `page.getByRole()`, etc.).

2. **JS `ComponentLocator`** (`index.js`, `ComponentLocator` class) — A thin JS wrapper that uses `nativeBinding.componentClick/Fill/Evaluate/etc.` and inline `document.querySelector()` evaluations. Lives in component-testing mode only.

The current state means `ComponentLocator` has no access to Rust's actionability checks (wait-for-element-stable, wait-for-visible, wait-for-enabled), get-by semantics, or chaining. It essentially reimplements the Playwright API poorly.

The Rust `JsLocator` already has `napi` annotated methods — but `ComponentLocator` operates on `page_id` + raw selectors, not through the Rust locator object.

## Goals / Non-Goals

**Goals:**

- Expose `JsLocator` and `JsFrameLocator` from the napi module as first-class JS objects
- Add `.locator(selector)`, `.frameLocator(selector)`, and all `getBy*` methods to `ComponentLocator`
- Route all existing `ComponentLocator` actions through the Rust locator for proper actionability checks
- Eliminate the `nativeBinding.componentClick/Fill/Evaluate` napi exports in favor of the locator path

**Non-Goals:**

- Not changing the Rust `JsLocator` implementation itself (it already works)
- Not overhauling the existing `Component` class API surface
- Not adding new locator features beyond what `JsLocator` already has

## Decisions

### Decision 1: JsLocator already has napi annotations — expose it as a JS class

`JsLocator` in `src/locator.rs` already uses `#[napi]` on its impl block. The napi bindings are auto-generated by the napi-rs build. However, the JS side (`index.js`) never imports or references these — it uses the separate `nativeBinding.component*` functions instead.

**Path forward**: Export `JsLocator` from the napi module, then `ComponentLocator.locator(sel)` returns a `new nativeBinding.Locator(pageId, selector)`. This gives JS a real Rust-backed locator object.

**Alternative considered**: Rewrite `ComponentLocator` entirely in Rust as a napi class. Rejected because `ComponentLocator` is tied to the component lifecycle (closed state tracking, mount context) better handled in JS.

### Decision 2: Bridge, don't replace ComponentLocator

`ComponentLocator` has state (`_pageId`, `_selector`) and a closed-check pattern. Rather than replacing it with a pure Rust object, we bridge: `ComponentLocator` creates a `JsLocator` internally for all operations.

Specifically:

```js
class ComponentLocator {
  constructor(pageId, selector) {
    this._pageId = pageId;
    this._selector = selector;
    this._inner = new nativeBinding.Locator(pageId, selector);
  }

  async click(options) {
    return this._inner.click(options);
  }

  async fill(value, options) {
    return this._inner.fill(value, options);
  }

  locator(selector) {
    return new ComponentLocator(this._pageId, `${this._selector} >> ${selector}`);
  }

  getByRole(role, options) {
    // delegate to JsLocator's get_by_role
    const loc = this._inner.getByRole(role, options?.name ? { name: options.name } : undefined);
    return new ComponentLocator(this._pageId, loc._selector);
  }
  // ... etc
}
```

### Decision 3: Expose JsLocator's napi-created instances

`JsLocator::get_by_role()` and similar return new `JsLocator` instances with updated selectors. The bridge needs to extract the selector from the Rust locator. We must ensure the `selector` field on `JsLocator` is accessible from JS — it already is (it's a `#[napi]` public field).

### Decision 4: Replace componentClick/componentFill/etc. with locator-based equivalents

Rather than having two code paths (napi `componentClick` and `JsLocator.click`), the bridge approach means:

- `JsLocator.click()` handles CDP action with built-in actionability waits
- The old `nativeBinding.componentClick()` becomes unused
- We keep the napi export for backwards compat but deprecate it

## Risks / Trade-offs

- **Bridging adds an extra JS wrapper layer** — Negligible perf impact; the heavy work is in Rust
- **`JsLocator` selector prefix scoping** — When doing `ComponentLocator.locator('button')`, we need to compose selectors. The existing `>>` chaining in `JsLocator` already handles this via `JsLocator::locator()`
- **Backwards compat** — Existing `Component.click(sel)` and `Component.fill(sel, val)` on the `Component` class (not `ComponentLocator`) use the old napi bindings. We leave those untouched — they're convenience shorthands
- **Options forwarding** — `JsLocator` actions accept options objects; `ComponentLocator` needs to forward them properly. We'll use simple rest/spread forwarding
