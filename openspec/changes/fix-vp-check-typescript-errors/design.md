## Context

The project uses a NAPI-RS native addon with a JS wrapper (`index.js`) that exports both Rust-generated bindings and hand-written JS classes (e.g., `launch`, `ComponentLocator`, `Component`). The `index.d.ts` is auto-generated by napi-rs and only covers Rust-exposed symbols — all JS wrapper code is invisible to the type system.

TypeScript is checked via `vp check` (oxlint with `typeAware: true` and `typeCheck: true`), which processes all `.ts` files in the workspace. The root `tsconfig.json` only includes `*.ts` and `__test__/**/*.ts`, leaving `src/runtime/*.ts` without proper type resolution.

## Goals / Non-Goals

**Goals:**

- Eliminate all 82 TypeScript errors reported by `vp check --fix`
- Complete `index.d.ts` to fully describe the public JS API
- Ensure all source files get correct type resolution from tsconfig
- Fix `packages/trace-viewer/vite.config.ts` to type-check cleanly

**Non-Goals:**

- No runtime behavior changes
- No refactoring of JS or Rust code
- No reorganization of the API surface
- No changes to the NAPI-RS generation pipeline

## Decisions

### 1. Inline type declarations in `index.d.ts` (not a separate `.ts` source)

The `index.d.ts` is auto-generated by napi-rs. Rather than modifying the generation pipeline or splitting declarations into a separate file, add the missing declarations directly into `index.d.ts` in a clearly marked section. This keeps declarations co-located with the auto-generated types they augment.

### 2. `Page` as an interface (not class)

The `Page` type comes from the Rust NAPI binding as a class/interface. We augment it with declaration merging — adding methods like `goto`, `locator`, `close`, `content`, `title`, `url`, `evaluate` as interface members. The actual implementations exist in the Rust-generated bindings; we're just describing the existing API shape.

### 3. `Browser` as a minimal interface

`Browser` objects are returned from `nativeBinding.launch()` and expose `newContext()`, `close()`, and similar methods. Declare a minimal interface with just the methods used by test files and the wrapper.

### 4. No separate `src/` tsconfig

Adding `src/runtime/**/*.ts` to the root `tsconfig.json` `include` array is simpler than creating a separate tsconfig. Since these files use Node.js builtins and the root tsconfig already has `"types": ["node"]`, they'll type-check correctly once included.

### 5. trace-viewer vite.config uses vite's own `defineConfig`

The `packages/trace-viewer/vite.config.ts` imports `defineConfig` from `vite-plus`, but the package only depends on `vite`. Switch to `import { defineConfig } from "vite"` (which is available as a dependency) to resolve the plugin type mismatch.

### 6. Bump lib to `ES2024`

`Promise.withResolvers()` (used in `js/src/injected-actions.ts`) requires ES2024. Adding `"ES2024"` to the `lib` array in root tsconfig resolves this without changing the `target` (which remains `ES2022` for output — `lib` and `target` are independent).

## Risks / Trade-offs

- **Risk**: Manually maintained declarations in `index.d.ts` could drift from `index.js` over time.
  **Mitigation**: Keep declarations minimal — only declare what's actually exported. The `vp check` pipeline will catch drift.

- **Risk**: Adding `src/runtime/**/*.ts` to tsconfig `include` may pull in unintended files if the folder grows.
  **Mitigation**: The `include` pattern is specific to `src/runtime/` — new subdirectories won't be auto-included.
